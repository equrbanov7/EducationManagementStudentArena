## Findings

### F-01 [Critical] Non-admin members can open organization member and role pages

- Classification: Confirmed bug
- Severity: Critical
- Affected roles: Teacher, Student
- Likely additionally affected: Staff / generic member
- Reproduction steps:
  1. Log in as a non-admin member in an active organization.
  2. Open `/organizations/<org-slug>/members/`.
  3. Open `/organizations/<org-slug>/roles/`.
- Expected result:
  - Only org owner/admin-level users should see the full member directory and role-permission matrix.
  - Non-admin members should get a 403 or a redirect to a safe page.
- Actual result:
  - Both teacher and student accounts received HTTP 200 and could view the full member list and organization roles/permissions.
- Evidence:
  - Manual browser results captured from role sessions during the audit.
  - Automated regression coverage:
    - `tests/e2e/test_known_regressions.py::test_student_cannot_open_org_members_page`
    - `tests/e2e/test_known_regressions.py::test_student_cannot_open_org_roles_page`
- Probable root cause:
  - `apps/organizations/views.py:18-28` grants organization access to any active membership.
  - `apps/organizations/views.py:169-248` reuses that broad access check for members and roles pages instead of enforcing admin-level authorization.

### F-02 [High] Pending organization owner can access the organization before approval

- Classification: Confirmed bug
- Severity: High
- Affected roles: Organization owner / applicant
- Reproduction steps:
  1. Register a new organization owner through the real signup flow.
  2. Verify OTP but do not approve the organization as superadmin.
  3. Open `/organizations/<pending-org-slug>/`.
- Expected result:
  - Pending organizations should be blocked from normal tenant access until explicitly approved.
- Actual result:
  - The pending owner could access the organization dashboard before approval.
- Evidence:
  - Manual browser verification with the owner account before superadmin approval.
  - Automated regression coverage:
    - `tests/e2e/test_known_regressions.py::test_pending_owner_cannot_access_pending_org_dashboard`
- Probable root cause:
  - `apps/organizations/views.py:18-28` treats ownership as unconditional access.
  - `apps/organizations/views.py:42-63` and `apps/organizations/views.py:101-103` gate on `is_active` but not on `status == "active"`.

### F-03 [High] Join-organization selection is lost in the signup wizard

- Classification: Confirmed bug
- Severity: High
- Affected roles: Teacher, Student, Staff joining an existing organization
- Reproduction steps:
  1. Open `/accounts/register/`.
  2. Choose a join-existing-organization persona.
  3. Select an organization from the search dropdown.
  4. Continue to the account-details step and complete signup.
- Expected result:
  - The selected organization should be preserved and stored as the requested/join target.
- Actual result:
  - The visible search field still showed the selected label, but the hidden select lost its value.
  - The created user ended up with no organization join request and no organization linkage.
- Evidence:
  - Manual browser inspection of the hidden join field during the wizard.
  - Database verification after signup showed:
    - `profile.organization = None`
    - `profile.requested_organization = None`
    - no membership / join request rows
- Probable root cause:
  - `apps/accounts/static/accounts/js/register_wizard.js:326-355` filters against `organization.name` only.
  - `apps/accounts/static/accounts/js/register_wizard.js:381-400` writes the visible label as `Name (Country)` and then later re-filters against that full label, which no longer matches the plain `organization.name`.

### F-04 [High] Started exams cannot be resumed through the normal `/start/` route

- Classification: Confirmed bug
- Severity: High
- Affected roles: Student
- Reproduction steps:
  1. Start a private exam with `max_attempts_per_user = 1`.
  2. Leave the attempt in progress.
  3. Revisit `/exams/<exam-slug>/start/`.
- Expected result:
  - The student should be routed back into the existing in-progress attempt.
- Actual result:
  - The start route rejects the user as if all attempts were already used.
  - The in-progress attempt also disappears from the assigned-exam list because the list filters by remaining attempts.
- Evidence:
  - Manual seeded repro with a dedicated in-progress attempt user.
  - Automated regression coverage:
    - `tests/e2e/test_known_regressions.py::test_in_progress_exam_can_resume_via_start_url`
- Probable root cause:
  - `apps/exams/views/student/attempts.py:47-63` calls `exam.can_user_start()` before `_start_or_resume_attempt()`.
  - `apps/exams/domain/exam_definition.py:208-214` counts every non-draft attempt, including `in_progress`, as a consumed attempt.

### F-05 [Medium] Finishing an exam triggers the browser unsaved-changes confirmation dialog

- Classification: Confirmed bug
- Severity: Medium
- Affected roles: Student
- Reproduction steps:
  1. Start an exam attempt.
  2. Answer a question.
  3. Click the finish button and confirm the finish modal.
- Expected result:
  - The exam should submit immediately without an additional browser-level leave warning.
- Actual result:
  - A `beforeunload` confirmation is raised during form submission.
- Evidence:
  - Browser session entered a `beforeunload` modal state when finishing a real attempt.
- Probable root cause:
  - `apps/exams/templates/exams/student/take_exam.html:775-780` always enables the unsaved-changes warning while `hasUnsavedChanges` is true.
  - `apps/exams/templates/exams/student/take_exam.html:821-829` submits the form without first clearing the unsaved-changes state.

## Likely bug / needs product confirmation

### L-01 Blind grading behavior for assignments may be intentional, but is risky

- Classification: Likely bug / product-risk
- Affected roles: Teacher, Student
- Observation:
  - Teacher review showed anonymized student identity before grading.
  - Student grade visibility remained delayed behind the review lock window after grading.
- Why this is risky:
  - It may be intended blind grading, but it is surprising in the assignment flow and could confuse instructors unless clearly designed and documented.
- Recommendation:
  - Confirm whether assignment review is intentionally anonymous.
  - If yes, expose that expectation explicitly in the UI.

## Test blocker

### T-01 Full password-reset and OTP-expiry automation is not yet harnessed

- Reason:
  - The current local/CI path uses console email output, but there is no reusable inbox-capture or controllable time-travel helper in the E2E suite yet.
- Impact:
  - Basic password-reset page access is covered, but complete end-to-end reset / expiry automation remains incomplete.
- Recommendation:
  - Add a mail capture helper or deterministic management API for test-only OTP extraction and expiry control.

## Recommendations

1. Fix the organization authorization model first. The member-directory and role-matrix exposure is the highest-risk issue in the platform.
2. Add organization `status == "active"` enforcement everywhere tenant access is granted, especially for newly created owner organizations.
3. Rework the exam attempt lifecycle so `in_progress` attempts resume cleanly and do not consume the final allowed attempt before submission.
4. Clean up CSP and localization debt next, because those frontend issues are affecting critical auth and assessment pages.
5. Keep the new xfail regressions in CI until the underlying bugs are fixed, then convert them into normal passing assertions.
