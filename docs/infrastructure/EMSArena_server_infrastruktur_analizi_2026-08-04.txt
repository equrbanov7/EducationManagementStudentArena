1. QISA YEKUN QƏRAR
===================

1. Mövcud HPE DL360 Gen10-da müşahidə olunan cari yük zamanı CPU istifadəsi
   aşağıdır. Bu, 3 000 nəfərlik imtahan tutumunun sübutu deyil; amma ilkin
   prioritet CPU dəyişməkdən əvvəl host SPOF-u, RAM və şəbəkəni düzəltməkdir.

2. Əsas risk sistemin hamısının bir fiziki hostda olmasıdır. 12 app replika
   olsa da PostgreSQL, Redis, Nginx, media, backup, monitoring və app-lər eyni
   server söndükdə birlikdə dayanır. Bu, proses səviyyəsində replika olsa da
   host səviyyəsində HA deyil.

3. Mövcud server saxlanılmalı və gücləndirilməlidir:
   - RAM iki CPU üzrə simmetrik və kanal-balanslı artırılmalıdır;
   - minimum dual 10 GbE NIC əlavə edilməli, platforma 25 GbE-ready olmalıdır;
   - disklərin fiziki sayı, wear/SMART, controller cache və firmware iLO/SSA
     ilə yoxlanmalıdır;
   - 3.54 TiB istifadə olunmayan LVM sahəsi planlı şəkildə ayrılmalıdır;
   - production data, Docker, log və backup eyni root filesystem-də
     saxlanmamalıdır.

4. 15 000 qeydiyyatlı istifadəçi üçün ən balanslı seçim "ORTA BÜDCƏ" modelidir:
   mövcud server daxil olmaqla 3 müstəqil container/compute host, 3 PostgreSQL
   data nüsxəsi, 3 üzvlü quorum/DCS, iki load balancer və VIP,
   ayrılmış Redis workload-ları, dual-controller media/object storage, ayrıca
   immutable backup serveri, iki switch, iki firewall və iki UPS enerji xətti.

5. Hesablamanın əsas dizayn hədəfi 3 000 eyni-vaxtlı standart imtahan
   istifadəçisi, sertifikasiya testi isə ən az 4 500 istifadəçi olmalıdır.
   Bunlar ölçülmüş cari capacity deyil, ilkin planlama fərziyyəsidir; yalnız tam
   imtahan axını, failover və məlumat bütövlüyü testindən sonra təsdiqlənə bilər.
   Bütün 15 000 nəfərin eyni anda imtahana girməsi tələb olunarsa bu ayrıca
   "15K concurrency" layihəsidir və yüksək büdcə arxitekturası da əlavə app
   node-ları ilə böyüdülməlidir.

6. Avadanlıq alınmasından əvvəl P0 əməliyyat riskləri bağlanmalıdır:
   - paylaşılmış SSH credential-i dərhal ləğv etmək, digər production
     secret-ləri dependency-aware planla mərhələli rotasiya etmək;
   - .env və backup .env fayllarını 0600, yalnız deployment owner üçün etmək;
   - dirty production checkout-dan image build etməyi dayandırmaq;
   - off-host + immutable backup və real restore testi qurmaq;
   - PostgreSQL WAL arxivləmə/PITR və standby qurmaq;
   - SSH-ni VPN/management VLAN-a məhdudlaşdırmaq;
   - OS security update və tələb olunan reboot-u planlı icra etmək.

- PostgreSQL: 20 GiB RAM limit, CPU hard cap yoxdur.
- Redis: 4 GiB RAM, 2 CPU.
- Nginx: 512 MiB RAM, 4 CPU.
- PgBouncer: 512 MiB RAM, 1 CPU.

Vacib limit problemi:

- App, Nginx, PostgreSQL və PgBouncer PID 1 üçün soft nofile = 1024-dur.
- Nginx worker_connections = 1024, worker_processes = auto (80 worker).
- Canlı PgBouncer max_client_conn = 1000, default pool = 200 və reserve pool =
  40-dır; proses soft nofile=1024 olduğuna görə client limiti ilə descriptor
  ehtiyatı arasında təhlükəli dərəcədə az fərq qalır.
- Canlı pool_mode=transaction-dır, versiyalanmış compose default-u isə
  session-dır. RLS_TRANSACTION_SCOPED ilə birlikdə effective .env snapshot-ı
  alınmadan PgBouncer və ya bütün stack recreate edilməməlidir.
- Nginx-də limit hər worker üçün tətbiq olunsa da hər proxy connection client və
  upstream daxil olmaqla bir neçə file descriptor işlədə bilər. Buna görə sadə
  worker_connections vurması real client tutumu deyil.
- 4 CPU quota verilmiş Nginx konteynerində hostun 80 CPU-suna görə 80 worker
  açılması uyğunsuzdur və ölçülərək explicit worker sayı verilməlidir.
- Bu vəziyyət 15 000 WebSocket və ya çoxlu paralel uzun connection üçün hazır
  deyil. Nofile limiti gözlənilən client x hər connection üçün FD + upstream,
  log və ehtiyat formulu ilə hesablanmalı; container ulimit, systemd, Nginx
  worker_rlimit_nofile və PgBouncer birlikdə staging-də yoxlanmalıdır.

6. BACKUP VƏ DISASTER RECOVERY AUDİTİ
=====================================

Mövcud müsbət cəhətlər:

- Docker sidecar hər gecə 00:00-da pg_dump yaradır.
- Retention: 7 daily, 4 weekly, 3 monthly.
- Ayrıca systemd timer hər gecə 02:00-da timestamp-li pg_dump yaradır.
- Systemd dump gzip integrity check edir və 60 gün saxlayır.
- 2026-08-04 tarixli son iki backup uğurludur.

Kritik çatışmayanlar:

- Hər iki backup eyni fiziki serverin eyni controller-reported RAID 1+0 logical
  volume failure domain-indədir.
- Bir nüsxə repo qovluğundadır, digəri /var/backups altındadır; host/RAID
  itəndə ikisi də itir.
- Off-site, offline və ya immutable backup sübutu yoxdur.
- Media volume üçün avtomatik off-host backup sübutu yoxdur.
- PostgreSQL archive_mode off olduğu üçün WAL archive və PITR yoxdur.
- Real restore testinin uğurlu nəticə artefaktı tapılmadı.
- Replikasiya da backup deyil: səhv silinmə və ransomware standby-a keçir.

Cari faktiki RPO/RTO:

- Yalnız dump-a əsaslansa, məlumat itkisi 22-24 saata qədər ola bilər.
- Tam host itkisi üçün RTO ölçülməyib və off-host nüsxə olmadığına görə
  zəmanət verilmir.

Tələb olunan minimum:

- PostgreSQL base backup + fasiləsiz WAL archive, pgBackRest/WAL-G kimi
  yoxlanmış alətlə PITR.
- Eyni kampusda ayrıca backup repository.
- Başqa bina/site və ya cloud-da şifrəli immutable/offline nüsxə.
- DB ilə birlikdə media, deployment manifestləri, sertifikatlar, şifrəli
  secret escrow və restore runbook-u.
- Hər ay isolated restore testi; hər kritik imtahandan əvvəl restore smoke.
- Backup age, WAL lag, archive failure, storage dolması və restore-test age
  üçün alert.
- Backup tutumu sabit disk sayı ilə deyil, qorunan məlumat x gündəlik dəyişmə
  faizi x retention müddəti / ölçülmüş compression-dedupe nisbəti + ən az 30%
  boş yer formulu ilə hesablanmalıdır. Media və DB üçün ayrıca artım proqnozu
  verilməlidir.

İmtahan datasına hədəf:

- "Uğurlu saxlanıldı" cavabı verilmiş autosave/submit üçün arzu olunan RPO=0.
- Bu hədəf yalnız synchronous_commit, synchronous_standby_names, çatmış
  standby-a promotion, dayanıqlı WAL, split-brain fencing və tətbiqin yalnız DB
  commit-dən sonra ACK verməsi ilə mümkün sayılır.
- Eyni-site DB nasazlığı: RTO 10-30 dəqiqə.
- Tam site itkisi: orta modeldə RPO <=15 dəqiqə, RTO <=4 saat.
- Off-site RPO üçün archive_timeout, WAL upload SLO-su, replication lag həddi və
  köhnə standby-nın promotion edilməməsi qaydası ayrıca konfiqurasiya olunur.
- Bu rəqəmlər rəhbərlik tərəfindən Business Impact Analysis ilə təsdiqlənməlidir.


7. ŞƏBƏKƏ, STATİK IP VƏ GİRİŞ QATI
==================================

Cari vəziyyət:

- Server 10.0.2.42/19 ünvanını DHCP ilə alır.
- 4 x 1 GbE portdan yalnız biri aktivdir; bonding yoxdur.
- UFW aktivdir, default incoming deny-dir.
- 22, 80 və 443 TCP UFW-də Anywhere/IPv6 üçün açıqdır. Server RFC1918
  ünvanındadır; bu, internetdən birbaşa açıq olduğunu sübut etmir, amma upstream
  firewall/NAT-dan serverə çata bilən bütün L3 mənbələrinə icazə verir.
- Grafana, Prometheus və Alertmanager yalnız 127.0.0.1-ə bind olunub.
- Nginx-in /metrics/ marşrutu RFC1918 mənbələrinə açıq ola bilər; yalnız ayrıca
  monitoring subnet/service identity ilə məhdudlaşdırılmalıdır.
- PostgreSQL və Redis public host portuna bind olunmayıb - bu müsbətdir.
- SSH root login bağlıdır, public key işləyir, amma password auth aktivdir.
- Fail2ban-da sshd jail aktivdir.
- eno7-də boot-dan sonra təxminən 37.3 milyon RX paketindən 3.15 milyon host
  səviyyəli RX drop görünüb; hardware error/drop counter-i 0-dır. Multicast,
  queue/buffer və host-stack səbəbi ayrıca paket capture və NIC metriki ilə
  araşdırılmalıdır.

Statik public IP serverin özünə verilməməlidir. Düzgün yol:

Internet / kampus WAN
  -> HA firewall/VPN
  -> public static IP və NAT
  -> load-balancer virtual IP (VIP)
  -> ən az 2 app host
  -> private DB/cache/storage VLAN-ları

Daxili ünvanlar ya statik netplan, ya da sənədləşdirilmiş DHCP reservation
ilə sabit olmalıdır. Load balancer VIP serverin tək NIC ünvanından ayrılmalıdır.

Load balancer əlavə edilərkən real client IP itirilməməlidir. Yalnız allowlist
edilmiş LB ünvanlarından PROXY protocol və ya Nginx set_real_ip_from /
real_ip_header qəbul edilməli, origin-ə birbaşa giriş bloklanmalıdır. Cari IP
əsaslı 200 request/s və limit_conn 1000 qaydaları kampus NAT-ı və ya LB IP-si
arxasında bütün istifadəçiləri bir client kimi bloklaya bilər; rate-limit,
audit, IP allowlist və 3 000 WebSocket ssenarisi birlikdə test edilməlidir.

Repo/deployment-də imtahan zalı cihazını yoxlamaq üçün host ARP cədvəlinə baxan
arp-agent var. MAC ünvanı router/VLAN/LB sərhədini keçmir və multi-host HA-da
hər node eyni məlumatı görməz. Bu yoxlama NAC/switch-controller/DHCP
source-of-truth və ya idarə olunan cihaz sertifikatı ilə əvəzlənməli; routed və
failover ssenarisi ayrıca qəbul testindən keçməlidir.

Minimum VLAN-lar:

1. User/exam hall VLAN
2. DMZ/load balancer VLAN
3. Application VLAN
4. Database VLAN
5. Storage/media VLAN
6. Backup VLAN
7. Management/iLO/SSH VLAN
8. Monitoring VLAN
9. Coding sandbox VLAN, əgər coding exam aktiv olacaqsa

VLAN siyahısı özü izolasiya deyil. Zonalararası ACL matrisi default-deny
olmalı, hər istiqamət və port sənədləşdirilməli; iLO yalnız MFA-lı VPN/bastion
üzərindən management VLAN-da əlçatan olmalıdır.

SSH yalnız VPN/bastion + management VLAN-dan açıq olmalıdır. 22/tcp Anywhere
qaydası ləğv edilməli, password auth key-lər təsdiqləndikdən sonra bağlanmalıdır.

TLS:

- Cari sertifikat öz-özünə imzalanıb və 10.0.2.42 IP-si üçündür.
- Yalnız idarə olunan daxili cihazlarda universitet CA-sı quraşdırılıbsa bu
  qəbul edilə bilər.
- Public giriş üçün DNS adı və etibarlı public CA sertifikatı lazımdır.

- backup: 1 ayrıca immutable repository serveri + 1 off-site nüsxə hədəfi;
- Redis: cache/Channels üçün 3 data node, broker üçün ayrıca 3 data node;
  kiçik instansiyalar compute hostlarda yerləşə bilər, resursları ayrıca ayrılır;
- şəbəkə: 2 x 25 GbE-ready managed switch, 2 x HA firewall;
- enerji: 2 x online UPS, 2 x PDU/enerji xətti və generator inteqrasiyası;
- ehtiyat: hər disk sinfindən ən az 1 ədəd, 1 PSU, 1 NIC, fan, kabellər və
  switch portlarının 20-30% boş ehtiyatı.

Yüksək büdcə reference:
- primary site: 4 compute + 3 DB + minimum 4 object-storage node;
- edge: 2 load balancer, 2 firewall və 2 core switch;
- backup: ölçülmüş retention-a uyğun 1 və ya daha çox immutable repository;
- DR site: minimum 2 compute + 1 DB standby + storage replica, 2 firewall və
  2 switch; site promotion ilkin mərhələdə manual/idarə olunandır;
- coding aktivdirsə əlavə 2-3 izolə runner serveri;
- hər site üçün iki UPS/PDU xətti, generator və kritik komponent üçün vendor
  SLA-sına uyğun on-site spare dəsti.

Rack U, enerji (W/kVA), soyutma, optics/DAC uzunluğu və real disk sayı vendor
modeli seçildikdən sonra ayrıca fiziki survey və power budget ilə təsdiqlənir.


12. MÖVCUD SERVER ÜÇÜN KONKRET UPGRADE PLANI
============================================

12.1. RAM

- Təcili minimum: CPU2 tərəfində HPE population rule-a uyğun eyni 64 GB DIMM
  ilə 128 GB simmetrik konfiqurasiya.
- Tövsiyə olunan orta hədəf: hər CPU-nun 6 kanalını balanslayan 192 GB
  (məsələn 12 x 16 GB) və ya 384 GB (12 x 32 GB) HPE-compatible RDIMM.
- Mövcud 64 GB DIMM-in saxlanması/qarışdırılması yalnız HPE memory population
  matrix və vendor testi ilə edilməlidir.

12.2. Şəbəkə

- Dual-port 10 GbE minimum, server və switch 25 GbE-ready olmalıdır; 25 GbE
  replication/rebuild/backup-window benchmark-ı əsaslandırarsa alınır.
- Portlar iki fərqli switch-ə bağlanmalı, bonding/MLAG test edilməlidir.
- iLO ayrıca management VLAN-a bağlanmalıdır.

12.3. Disk/LVM

Mövcud 3.54 TiB free extent istifadə oluna bilər, amma kor-koranə root-a əlavə
etmək düzgün deyil. 3.64 TiB PV üçün bir konkret başlanğıc nümunəsi:

- OS/root: 200 GiB;
- Docker image/container data: 300 GiB;
- PostgreSQL: 600 GiB;
- media: 1 100 GiB;
- Prometheus/Loki/log: 300 GiB;
- təxminən 1 227 GiB, yəni 33% unallocated/free ehtiyat.

Bu rəqəmlər growth ölçümündən sonra dəyişdirilə bilər. Ayrı LV və mount-lar
dolma riskini idarə edir, amma eyni RAID üzərində olduqları üçün fiziki I/O və
hardware failure-domain izolyasiyası yaratmır.

DB, media və Docker volume köçürülməsi backup + maintenance ilə edilməlidir.
17.65 GB reclaimable build cache təsdiqdən sonra təmizlənə bilər; audit zamanı
destruktiv prune icra edilməyib.

12.4. Firmware və hardware health

- HPE SSA/ssacli və iLO ilə fiziki disk sayı, model, wear, predictive failure;
- P408i-a cache və battery/capacitor status;
- BIOS, iLO, Smart Array və SSD firmware;
- fan, temperatur, PSU və ECC error history;
- hər PSU-nun fərqli UPS/PDU xəttində olması.


13. YÜK TESTİ VƏ QƏBUL MEYARLARI
================================

Satınalma və rollout qərarı aşağıdakı test olmadan verilməməlidir:

1. Representative staging; production-a bənzəyən DB cardinality.
2. Ən az 4 500 unikal synthetic tələbə.
3. Bir neçə source IP/load-generator; tək IP Nginx 200 r/s və limit_conn 1000
   hədlərinə dəyir. Trusted real-IP və kampus NAT ssenarisi ayrıca yoxlanılır.
4. Tam flow:
   login -> waiting/start -> question -> autosave -> readback -> submit -> result.
5. 30-40 saniyəlik autosave və deadline-da eyni-anlı submit herd.
6. 3 000 WebSocket + reconnect storm; yüksək modeldə 7 500/15 000.
7. Elektron jurnal: davamiyyət, LessonMark, toplu grade import/export.
8. Ən uzun imtahan müddətinin ən az 2 qatı soak test.
9. Yük altında bir app hostun söndürülməsi.
10. Yük altında PostgreSQL primary failover.
11. Redis/broker dayanması, disk dolması və qısa şəbəkə kəsintisi.
12. Autosave/submit DB reconciliation: acknowledged data loss = 0.
13. ARP/MAC imtahan girişinin VLAN, LB və app-host failover ssenarisi.
14. PostgreSQL failover-da leader endpoint, PgBouncer drain və stale
    connection-ların bağlanması.
15. ethtool/ring/IRQ/softnet ilə NIC və kernel drop sayğacı; soak zamanı
    izahsız davamlı artım olmamalı, end-to-end packet loss <0.1% olmalıdır.
16. Aktiv LB/VIP node, bir link/switch/MLAG yolu, firewall, NAS controller/
    storage path, object gateway və bir PSU/UPS enerji xəttinin ayrıca itkisi.

İlkin SLO/qəbul hədəfləri:

- HTTP error rate <0.1%.
- Autosave p95 <2 saniyə.
- Submit p95 <3 saniyə.
- Adi read endpoint p95 <1.5 saniyə.
- Zero acknowledged-answer loss.
- Pikdə CPU <65%, RAM <70%, disk sahəsi <70%.
- DB/Redis/PgBouncer queue saturation yoxdur.
- Bir host itəndən sonra da SLO və minimum 30% headroom qalır.

SON NƏTİCƏ

Mövcud server atılmamalı: müşahidə olunan cari yükdə CPU az istifadə olunur,
amma 3K full-flow tutum hələ sübut edilməyib. Onu simmetrik RAM, minimum dual

Əsas investisiya ikinci və üçüncü failure domain, PostgreSQL standby/PITR,
ortaq media storage, ayrıca immutable backup, redundant network/UPS və
reproduksiya olunan deployment prosesinə getməlidir.

15 000 qeydiyyatlı istifadəçi üçün tövsiyə: ORTA BÜDCƏ modeli. 3 000 concurrent
dizayn və 4 500 stress rəqəmi ilkin sizing fərziyyəsidir; yalnız full-flow,
failover və zero-data-loss qəbul testindən sonra sertifikatlaşdırılır. Bütün
15 000 eyni anda tələb olunarsa satınalmadan əvvəl 20 000 istifadəçili
full-flow test və yüksək büdcə app/edge genişlənməsi məcburidir.
